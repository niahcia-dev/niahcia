# NIAHCIA Native Contract Runtime V1

Status: **CANDIDATE / REVIEW REQUIRED / INACTIVE**

## Purpose

Smart contracts are a core NIAHCIA base-chain requirement. This specification defines the boundary that must be completed before NativeTransaction V1 `ContractCall` or `ContractCreate` can become executable.

The existence of those transaction actions is already part of the native transaction model. What is not yet locked is the runtime that gives them deterministic consensus meaning.

## Architecture boundary

The contract runtime executes inside deterministic full-node state transition.

It is:

- subordinate to CPU Proof-of-Work consensus;
- validated independently by every full node;
- separate from decentralized AI inference;
- separate from optional storage/service providers;
- not dependent on an external EVM/Reth execution engine.

The chain must remain valid if every AI worker and optional service/storage provider disappears.

## Required deterministic surfaces

Before activation, V1 contract execution MUST define and vector at least:

1. canonical contract code/creation payload representation;
2. contract-address derivation and collision rules;
3. contract account/state representation;
4. canonical contract storage key/value representation and root commitment;
5. `ContractCreate` initialization semantics;
6. `ContractCall` input/output semantics;
7. nested call/depth rules if supported;
8. native NIAH value transfer into and out of contract execution;
9. success, revert, trap/failure, and out-of-gas semantics;
10. sender nonce behavior on accepted runtime failure;
11. deterministic gas/resource accounting;
12. memory/code/storage/stack limits;
13. receipt/output/log/event representation if supported;
14. state/execution commitment integration;
15. block persistence, restart, snapshot, and reorg behavior;
16. activation/version negotiation and canonical interoperability vectors.

## Determinism requirements

Consensus-valid contract execution MUST NOT directly access:

- network sockets or HTTP;
- filesystem state;
- host wall-clock time;
- randomness not explicitly supplied by consensus rules;
- GPU/AI inference;
- model APIs;
- host environment variables;
- nondeterministic syscalls;
- floating-point behavior whose consensus representation is not explicitly specified.

Any environmental/block context visible to a contract must be explicitly defined and identically derivable by every validating node.

## AI boundary

AI inference is off-chain service execution, not contract VM execution.

A contract MAY eventually verify explicitly specified deterministic evidence such as signatures, hashes, commitments, receipts, or proofs generated by off-chain AI/service protocols.

A contract MUST NOT make chain validity depend on an AI worker responding.

## ContractCreate payload boundary

The canonical creation payload is NCE/1 object type `0x0018`, schema V1:

```text
1 runtime_id
2 code
3 init_data
```

The enclosing NativeTransaction retains the already-locked action shape: `ContractCreate` has an empty `target_payload`, and its `data` field contains the complete canonical ContractCreatePayload V1 bytes.

V1 payload validation is intentionally separate from VM support:

- `runtime_id = 0` is reserved and invalid;
- non-zero runtime IDs are syntactically representable;
- an execution implementation MUST separately reject a runtime ID that is not activated for the current network/height;
- code MUST be non-empty and no larger than 65,536 bytes;
- init data MAY be empty and may be no larger than 65,536 bytes;
- code bytes and init-data bytes are distinct fields and MUST NOT be concatenated or guessed apart by a VM.

On successful creation, the persistent ContractStateV1 `code` field stores exactly the validated `code` bytes. `init_data` is constructor input and is not automatically appended to persisted code.

The canonical fixture is `test-vectors/native-contract-create-payload-v1.json`. The payload bytes are locked by the Rust `locked_contract_create_payload_vector_matches_json` test; incompatible payload changes require an explicit successor schema.

## Contract address derivation and collision rule

ContractCreate uses the locked Address V1 derivation domain:

`NIAHCIA/CONTRACT/V1`

with the transaction network ID, native chain ID, authenticated creator Account payload, and the creator transaction nonce.

The Bech32m text form is never part of the derivation input.

A successful ContractCreate MUST install contract state only at the exact derived Contract Address V1 payload. If persistent contract state already exists at that payload, creation MUST fail deterministically and MUST NOT overwrite or merge with the existing contract.

Address derivation itself does not mutate state.

Canonical derivation is locked by `test-vectors/contract-address-v1.json` and the reference implementation's `locked_contract_derivation_vector` test.

## Contract-capable state boundary

Persistent contract code, native value, and storage are defined by `spec/native-contract-state-v1.md`.

The candidate contract-capable successor state is NativeStateV3, which commits the exact NativeStateV2 root plus a separate domain-separated contracts root. NativeStateV2 bytes and roots are not reinterpreted.

Contract storage is fixed-width 32-byte keys and 32-byte values in canonical ascending-key order. Contract code remains opaque at this layer so VM selection remains a separate decision.

Native Contract State V1 is vectored by `test-vectors/native-contract-state-v1.json`; the vector locks contract-record bytes/hash, contracts root, NativeStateV3 root, and NativeStateV3 snapshot bytes without selecting a VM.

## State atomicity

Contract execution must use deterministic transactional semantics.

For an accepted transaction that reaches runtime:

- the account nonce behavior follows Native Transaction V1;
- successful state/value effects commit atomically;
- reversible contract/value effects are discarded on revert/failure according to the versioned runtime rules;
- fee/gas effects follow the versioned fee policy;
- no partial contract-storage mutation may survive a failed transition unless the specification explicitly makes that effect non-revertible.

## Gas

The contract gas schedule is not defined by this draft.

It must be native to NIAHCIA, deterministic, bounded, and versioned. It must not inherit host CPU timing or external-chain gas constants merely for convenience.

## Runtime technology

The exact VM/instruction technology is intentionally **not selected by this document**.

Selection must be based on:

- deterministic cross-platform execution;
- implementation simplicity/auditability;
- bounded resource use;
- tooling and developer ergonomics;
- long-term versionability;
- ability to create reproducible consensus vectors.

EVM compatibility may be evaluated as a compatibility option, but NIAHCIA does not require Reth/EVM as its base execution engine.

## Activation rule

`ContractCall` and `ContractCreate` MUST remain non-executable in the active reference node until:

- this runtime is concretely specified;
- state/storage commitment rules are specified;
- gas and failure semantics are specified;
- canonical vectors exist;
- persistence/restart/reorg behavior is tested;
- an explicit activation/version boundary is assigned.

Reserved transaction action values do not themselves activate smart-contract execution.
